# 高风险研发细则

仅在 `rules/product-dev.mdc` 判定高风险后读取；低/常规风险不加载。

## 高风险路径（例外，而非默认）

```text
需求分析 → 原型设计 → [人工审批] → 功能实现 → 测试验证 → [人工审批] → 合并上线
```

只有高风险变更必须按顺序通过；低风险与常规风险不应被此路径拖重。

### 阶段 1：需求分析

**产出**：风险明确的拆解文档（`docs/task-breakdown-*.md`）
**动作**：
1. 理解业务目标和用户价值
2. **聚焦过滤**：明确列出「不做什么」和「为什么不做」，与「做什么」同等重要
3. 判断是否真的属于高风险；如果不是，降回默认路径
4. 拆解为可执行子任务（用 Claude Code 原生 plan mode，把结果落到 `docs/task-breakdown-*.md` 或直接写入 `docs/approved/`）
5. 标注子任务间的依赖与并行关系
**审批**：仅当存在真实设计决策时，才需要人工确认后进入下一阶段

### 阶段 2：原型设计与实现

**产出**：可运行的原型系统 + 设计文档（直接写入 `docs/approved/`）
**动作**：
1. 将设计文档直接写入 `docs/approved/`（实体化命名，如 `design-approval-engine.md`），包含：
   - YAML frontmatter 元数据头（`approved_by: pending`，待人审批时更新）
   - 数据模型设计（ER 图或表结构）
   - API 接口设计（路由、请求/响应格式）
   - 核心流程的状态机或时序图
   - 技术选型与理由
2. 实现最小可运行原型（Prototype），仅覆盖核心路径
3. 原型必须可启动、可演示核心流程，但无需完善边界处理
4. 编写原型验证脚本或手动验证步骤
**提交**：只有当“设计确认”与“实现落地”存在真实决策边界时，才单独创建 `prototype:` PR；否则可在同一 PR 中以明确 commit / section 区分原型与落地

### ▶ 审批门禁：原型确认

**Agent 在此暂停，等待人工审批。**

审批内容：
- [ ] 数据模型是否合理
- [ ] API 设计是否符合现有规范
- [ ] 技术选型是否恰当
- [ ] 原型是否可演示核心流程
- [ ] 是否需要调整设计方向

审批方式：人在 PR 中直接编辑/修正 `docs/approved/` 下的设计文档，merge = 审批。

审批结果：
- **通过（merge）** → `docs/approved/` 中的文件成为符合性基线，进入功能实现阶段
- **需修改** → 人在 PR 中提出修改意见，Agent 修改后重新请求 Review
- **否决** → 终止当前方案，回到需求分析重新规划

### 阶段 3：功能实现

**产出**：生产级代码 + 测试 + 必要文档
**动作**：
1. 基于已审批的原型，补全所有边界处理和错误处理
2. 编写完整的测试套件（遵循 test-philosophy.mdc）
3. 将实现收敛到一个用户意图明确的 PR 中；只在确有必要时拆分
**提交**：PR 标题聚焦结果，不写冗长过程清单

### 阶段 4：测试验证

**产出**：验证摘要 + 验收确认（默认精简；高风险时再附扩展材料）
**动作**：
1. 运行完整测试套件，确保不破坏已有功能
2. 验证所有验收标准（AC）已覆盖
3. 检查 Story ↔ Test 对齐（无漂移）
4. 生成变更摘要：改了什么、为什么改、如何验证
**提交**：默认在同一 PR 中附带精简验证摘要；高风险变更才附完整验收矩阵与额外证据

### ▶ 审批门禁：合并确认

**Agent 在此暂停，等待人工审批。**

审批内容：
- [ ] 代码质量是否达标
- [ ] 测试覆盖是否充分
- [ ] 是否影响其他模块
- [ ] 是否可以合并到主分支
